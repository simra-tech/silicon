# Pinned IO tap reference applicability

Strict IO tap closure is **not established** under the held native geometry,
source parameters and rule deck. The existing source-prefix binding repair is
legitimate but insufficient: the compared tap is present and its terminal
mapping is consistent, while its area and perimeter still disagree. No new
LVS, electrical simulation, source correction or native-cell modification was
performed in this investigation.

## Why a reader reinterpretation does not close the mismatch

The pinned `custom_reader.lvs` creates `CustomTap` for a two-terminal resistor
whose model contains `tap`; it assigns TIE/WELL in source order. Its parameter
mapping is A or W×L, scaled to square micrometres, and P or PERIM or 2(W+L),
scaled to micrometres. It has no equivalent-square-to-layout transformation.
The unchanged `CustomTap` declares primary A/P parameters, with no custom
A/P tolerance override. The parallel combiner adds A and P for matching
TIE/WELL pairs; it does not reconstruct perimeter from total area.

The native extraction uses the derived tie geometry and substrate/well domains.
For the decisive local cell, independent raw-layer Boolean reconstruction
agrees exactly with the saved stock-extracted A/P:

| `sg13g2_LevelUpInv:XR0` | A (µm²) | P (µm) |
|---|---:|---:|
| Pinned CDL | 1.051 | 4.1 |
| Native / saved stock extraction | 1.053 | 7.62 |
| Native minus source | 0.002 | 3.52 |

The native tie is a hole-free Manhattan rectangle, 3.51×0.30 µm, at native
DBU bounds `[0, 8350, 3510, 8650]`, DBU 0.001 µm. Its perimeter is about
85.85% greater than the source value. Existing normalized TIE/WELL mapping
is consistent with the compared net pairs; a net-name rewrite would not
resolve the parameter difference.

All 63 tap records in 41 pinned source cells were inventoried with exact
decimal arithmetic. Excluding one literal unit defect discussed below, all
62 source perimeters are within about 0.018% of `4√A`. This is a numerical
equivalent-square pattern, **not proof of an authorized effective-geometry
interpretation for native guard rings**.

### Orthogonal-shape bound and rounding are separate

For a Manhattan region with area A and total boundary perimeter P,
`P² ≥ 16A` is necessary. For one connected component this follows from its
bounding-box width/height: P≥2(w+h), A≤wh. Applying the bound per component
also covers disconnected unions; holes cannot relax it. This statement is
**not** the general curved/non-Manhattan isoperimetric bound.

For the literal LevelUp source values, `P²−16A = −0.006 µm²`; fourteen of
the 63 exact source pairs fail the Manhattan necessary bound. That alone
does not prove an unrounded design is impossible: a 1.025 µm square has
A=1.050625 µm², which rounds to 1.051, and P=4.1 µm. Such rounding can
explain this tiny bound failure. It cannot explain the native rectangle's
P=7.62 µm. Even a hypothetical decimal-rounding accommodation would not
close the observed geometric discrepancy, and no deck tolerance was changed.

## Applicability to the current chip, not just library inclusion

Source-only binding checked all 4,884 original logical PNL instance/master
pairs against the current 4,904-instance round-trip ODB inventory. The only
20 additional instances are explicit IO fillers. All 140 IO instances use
13 masters present in both pinned CDL and native GDS.

The current hierarchy reaches `sg13g2_LevelUpInv` eight times: two each under
`pad10_gate`, `pad11_fault_n`, `pad16_sdo`, and `pad17_temp_out`, through
`sg13g2_GateLevelUpInv`. Exact instance paths and source lines are saved in
the reachability report. Thus the local mismatch is relevant to the current
source graph. This does not substitute for a new assembled fullchip LVS.

Two additional library observations are explicitly **not current blockers**:

- `sg13g2_io_inv_x1:XR0` literally has `P=3.16`, with no suffix. The unchanged
  reader, in a prefix-only diagnostic fixture, produces P=3,160,000 µm.
  Replacing it by `3.16u` is a plausible hypothesis, not an authorized source
  interpretation or implemented fix. This master has zero occurrences in
  the current reachable IO hierarchy.
- `sg13g2_Filler10000` uses `Perim`, which the pinned reader genuinely
  supports. Both records parse correctly. This master is also not used.

## Legitimate interface and consequential remedy

There is a pinned geometric ring symbol, `ptap1_ring.sym`. It emits
`A=2rw(w+l−2rw)` and `P=4(w+l−2rw)`, a different legitimate source interface
from an equivalent-area square. Its electrical expression also contains
twice that perimeter in its conductance term, whereas the rectangle
`ptap1.sym`/`CbTapCalc` uses the single perimeter. This audit does not certify
either expression for the stock IO guard geometry or interpret the extra
factor as a bug. Blindly substituting the ring symbol is not justified.

The pinned ngspice `ptap1`/`ntap1` model uses the supplied R; its W/L parameters
are declared but unused. Therefore changing physical A/P while silently
holding the old electrical R does not establish cross-view consistency.
The earlier conditional rectangle-formula calculation gives approximately
190.268 Ω from the LevelUp source A/P but 112.994 Ω from its native A/P;
neither number is a measured native guard resistance. This is an explicit
electrical-model consequence, not a resistance correction made here.

The in-scope conclusion is **unresolved source/native applicability**, with
these possible next directions requiring an explicit decision:

1. Obtain an authoritative, mutually consistent IO source/native view and
   documented physical/electrical tap interpretation from the public PDK
   maintainers. A new revision would require deliberate repinning and
   rerunning the relevant qualification. No upstream message was sent.
2. Propose a separately reviewed IO source-interface correction, retaining
   provenance and independently justified physical geometry and electrical
   intent. This is a source change, not syntax normalization. Merely copying
   extracted A/P into a golden reference would be circular and is not an
   acceptable independent closure proof.

Keeping the exact source/native/deck trio held does not offer a demonstrated
strict closure route. Altering the native tie to fit a square would modify a
pinned IO cell and still require electrical/ESD and geometric qualification;
it is not a read-only remedy.

The documented `--disable_tap_extraction` option omits this comparison;
`blank_circuit`, net-only comparison, or relaxed tolerances similarly do not
establish the requested strict tap match. These paths are not applicable to
this task. Public upstream reports corroborate that tap comparison and
overlapping-cell applicability are known issues, but provide no waiver or
qualification for this chip: [IHP issue 955](https://github.com/IHP-GmbH/IHP-Open-PDK/issues/955)
and [IHP issue 634](https://github.com/IHP-GmbH/IHP-Open-PDK/issues/634).

## Reproduction

Use the pinned runtime with one CPU, a 2 GiB RAM reservation, and a fresh
resource gate. Each command was bounded by at most 180 seconds; no simulation
batch was launched. Host-specific launch paths are deliberately excluded.

```sh
python3 audit_pinned_taps.py --output NEW_AUDIT --resource-gate RESOURCE_GATE_JSON
klayout -b -r probe_pinned_parameter_reader.rb -rd output_dir=NEW_READER_OUTPUT
python3 audit_reachability.py --roundtrip CURRENT_ROUNDTRIP_TSV --output NEW_REACHABILITY
```

Invoke the repository-relative script paths from the repository root.
Preserve existing output directories. The gate's sanitized identity and
actual run bounds are recorded in [run evidence](RUN_EVIDENCE.json).
