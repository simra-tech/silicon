# A source/native substrate topology counterexample

The current marker candidate fails strict LVS for a real terminal-partition
difference, independently of tap A/P. The following is a minimal witness,
not an attribution of every comparison failure to one cause.

Pinned KLayout 0.30.9 / IHP PDK `84374023ee8b4b126bebbba67fcbada0a9c0ff0b`.
Source `f4ce6848bd7dd179d2ef4cbd8a4ea6bf9788bcfa1ff4b93fabae8bf18b6378f9`;
native GDS `ae62bf68aa001144c08a37c58ac3553c6e5f2013a6824b340218e84962066aca`;
saved extraction `3ed5cd2b78b3d4f4ed724730fcba2388148340d6442249e143c17a9f7ac99f04`.

## Exact witness

The original source chain is `pad02_vss → sg13g2_IOPadVss.I2 →
sg13g2_DCPDiode.XR0`. The leaf record is:

```spice
XR0 guard sub! ptap1 A=33.524p P=23.16u
```

The independently qualified, reversible instance-prefix adapter makes this
original primitive visible to the pinned reader; it changes no node/model/A/P.
Its TIE is external IOVSS. Its WELL is the internal node
`PAD02_VSS.I2.SUB!`, connected to exactly this one terminal and no external
pin. In contrast, **every native PTAP WELL** is on the independently probed
external VSS net. There is therefore no native PTAP to which this source
device can map while preserving external pins and terminal connectivity.
No choice of A/P values can resolve that contradiction.

The 243 source-local WELL nodes contain 889 terminal incidences: 386 PTAP
WELL, 403 HV-NMOS bulk, 11 LV-NMOS bulk, 64 antenna-diode anodes and 25
RPPD substrate terminals. Thus this is not only a primitive-count issue.
The complete native VSS incidence inventory is saved separately; a native
global component contains core devices as well, so those whole-component
counts must not be misrepresented as pairwise IO device correspondence.

## What correction is—and is not—justified

The pinned library bytes were included intact. Neither `.GLOBAL` nor the CDL
`*.GLOBAL` form occurs in the full source. The held reader controls give two
separate substrate nodes with no declaration, one with the explicit correct
declaration, and two with an unrelated declaration. This is not a new
fullchip assembly omission or a justified inference from the `!` spelling.

Cadence's own explanation distinguishes the schematic `!` convention from
the explicit global declaration emitted to CDL; the suffix is not evidence
that this pinned source already contains that binding.
[Cadence: multiple power pads and global supply names](https://community.cadence.com/cadence_technology_forums/f/custom-ic-design/57227/multiple-power-pads-when-global-supply-name-used-in-sub-blocks).

A declaration making the 243 source nodes common would still not, by itself,
identify that common node with external VSS. That second connection also
requires justified design intent; it would short six native VSS-to-body tap
endpoints and change the effective source substrate circuit. VSS and IOVSS
must remain distinct external domains. No declaration, short, ignored tap,
comparison hint, model edit or native-parameter copy has been implemented.

The bounded next implementation, **only after a reviewed substrate-interface
decision**, is a separately named source derivative with explicit substrate
ports propagated through each affected IO hierarchy. Its exact terminal
partition must be audited against the approved body-domain specification,
with reverse-source restoration, unchanged device/model/A/P inventory and
wrong-domain negative controls. This makes the decision visible rather than
silently relying on global-name behavior. It would not resolve the separate
tap A/P/electrical applicability failure; that requires independent source
geometry/model evidence, not extraction-derived golden values.

The pinned geometry rules also distinguish the two choices: DigiSub removes
a narrow boundary from derived p-well, while unmarked p-taps connect that
well through contacts to metal. The named-substrate marker instead selects
the finite PTAP device. Thus the observed VSS body binding need not mean an
IOVSS-to-VSS metal short, and adding arbitrary DigiSub partitions is not an
electrically qualified repair. These are actual pinned rule semantics, not
permission to alter the deck or the library's body-domain specification.
[Pinned derivation rules](https://raw.githubusercontent.com/IHP-GmbH/IHP-Open-PDK/84374023ee8b4b126bebbba67fcbada0a9c0ff0b/ihp-sg13g2/libs.tech/klayout/tech/lvs/rule_decks/general_derivations.lvs),
[pinned connection rules](https://raw.githubusercontent.com/IHP-GmbH/IHP-Open-PDK/84374023ee8b4b126bebbba67fcbada0a9c0ff0b/ihp-sg13g2/libs.tech/klayout/tech/lvs/rule_decks/general_connections.lvs).

The pinned IO README distinguishes generated library views from the
externally contributed CDL and records its later regeneration. It does not
specify the missing global/body binding. The older generator therefore
cannot supply the current substrate contract without additional proof.
[Pinned IO README](https://raw.githubusercontent.com/IHP-GmbH/IHP-Open-PDK/84374023ee8b4b126bebbba67fcbada0a9c0ff0b/ihp-sg13g2/libs.ref/sg13g2_io/doc/README.md).
